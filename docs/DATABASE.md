# ForensicLens Database Design

**Product:** ForensicLens  
**PRD:** Version 1.1  
**Architecture:** `docs/ARCHITECTURE.md`  
**Database target:** SQLite + FTS5 for P0; PostgreSQL is the scale target.

## 1. Scope and database strategy

The schema covers only Base/Core features required for the P0 investigation workflow: case management, immutable evidence/provenance, normalized events and raw records, FTS/structured retrieval, sessions/timeline/patterns, entities/behaviour mappings, investigations/jobs, pseudonymization metadata, typed claims and verification, legal retrieval/elements, integrity findings, audit/reproducibility, benchmark runs, reports, and privacy configuration.

The architecture deliberately uses **one SQLCipher database per case** at `data/cases/<case_id>/case.db`. This is stronger isolation than a single global evidence database and makes export/deletion straightforward. The legal corpus is a separate global read-only store; it is not case evidence.

SQLite has no native PostgreSQL-style Row Level Security (RLS). Therefore:

- P0 SQLite isolation is enforced by the per-case database boundary, case-bound repository interfaces, authenticated API case ownership checks, and a separate read-only verifier connection.
- `backend/migrations/postgres/001_rls.sql` defines the equivalent PostgreSQL RLS policy contract for the planned scale migration.
- The PostgreSQL policy uses `current_setting('app.case_id', true)` as the request case context. Application code must set it only after authentication and case authorization.
- No client or LLM can set the case context directly.

## 2. Naming conventions

- Tables: plural `snake_case`, e.g. `evidence_files`.
- Columns: singular `snake_case`.
- Primary keys: `<entity>_id`, stored as opaque text IDs (UUIDv4/ULID generated by the application).
- Foreign keys: `<referenced_entity>_id`.
- Boolean columns: `is_*` or `has_*` and stored as `INTEGER NOT NULL CHECK (value IN (0,1))` in SQLite.
- Timestamps: UTC RFC3339/ISO-8601 strings with `Z`, stored as `TEXT` in SQLite; PostgreSQL migration uses `timestamptz`.
- Hashes: lowercase hexadecimal SHA-256 strings, `TEXT NOT NULL`.
- Enumerations: `TEXT` plus `CHECK` constraints in SQLite; PostgreSQL uses `CHECK` constraints rather than PostgreSQL enums for easier migration/versioning.
- JSON: canonical UTF-8 JSON in `TEXT`; validate at the application boundary.
- Human-readable text is UTF-8 and is never interpreted as instructions.
- Raw evidence is not stored as mutable database text; the database stores immutable object hashes and provenance while the original bytes live in the case content-addressed filesystem.

## 3. Entity relationships

```text
cases
 ├──< evidence_files ──< raw_records
 │          └──────────< events ──< event_entities >── entities
 │                         │  └──< session_events >── sessions
 │                         └──< integrity_findings
 │
 ├──< investigations ──< jobs
 │          └──────────< claims ──< claim_slots
 │                         ├──< claim_evidence >── events
 │                         └──< claim_verifications
 │
 ├──< privacy_configs
 ├──< audit_records
 ├──< behaviour_mappings
 └──< reports

Global legal store (separate DB)
 legal_provisions ──< legal_elements

Global benchmark store / benchmark metadata
 benchmark_runs
```

`claim_slots` stores typed entity references such as `USER_001` rather than raw PII. The encrypted vault is the authoritative token-to-value mapping and is outside the SQL schema. Verification resolves tokens through the vault before compiling predicates. Unknown tokens are `UNVERIFIED`.

## 6. Important derived indexes outside SQL

The architecture keeps Chroma per case. The SQL database stores the authoritative event IDs and metadata; Chroma stores derived embeddings and metadata references.

Each Chroma document must include at least:

```json
{
  "case_id": "CASE_...",
  "event_id": "EV_...",
  "embedding_model_hash": "...",
  "text_hash": "..."
}
```

Legal Chroma documents similarly reference `legal_id` and `source_hash`. A vector result is never treated as authoritative evidence until the referenced SQL record exists and belongs to the active case.

## 7. Access rules / RLS policy contract

### Case-bound tables

The following tables are case-scoped and must only be readable/writable when `case_id = active_case_id` and the authenticated principal owns/has access to that case:

`cases`, `evidence_files`, `raw_records`, `events`, `sessions`, `session_events`, `entities`, `event_entities`, `investigations`, `jobs`, `claims`, `claim_slots`, `claim_evidence`, `claim_verifications`, `behaviour_mappings`, `integrity_findings`, `privacy_configs`, `audit_records`, `reports`.

### Restricted write rules

- **Frontend/API principal:** can create/update permitted case metadata and initiate operations; cannot directly mutate evidence bytes, claims' verification status, audit hashes, or legal records.
- **Ingestion service:** may insert/update `evidence_files`, `raw_records`, `events`, entity links and integrity findings for its active case. It cannot write verified claims.
- **Retrieval/correlation:** read-only access to evidence/session/entity tables; may write derived sessions/entity mappings where the pipeline owns those stages.
- **Verifier:** read-only database connection to evidence, sessions and entities; may insert verification results through a separate trusted write path, but cannot modify evidence.
- **Privacy module:** may access case privacy config and vault. Vault values are not exposed to generic SQL clients.
- **Legal importer:** owns writes to the global legal KB. Investigation requests have read-only access.
- **Audit writer:** append-only; no UPDATE/DELETE of existing audit rows.
- **Report writer:** can create reports; cannot alter evidence or audit history.

### No-access rules

- LLM: no SQL, no Chroma, no filesystem, no vault, no shell, no arbitrary HTTP.
- Browser: no direct database/vector/vault/model access.
- Natural language: never translated into raw SQL.
- Evidence text: never interpreted as SQL, code or instructions.

The equivalent PostgreSQL `ENABLE ROW LEVEL SECURITY` policies are in `backend/migrations/postgres/001_rls.sql`. SQLite P0 relies on physical per-case databases plus trusted repository boundaries rather than pretending SQLite supports RLS.

## 8. Migration process

Use application-controlled migrations with an ordered, immutable migration directory:

```text
backend/migrations/
├── 001_initial.sql
├── 002_<future_change>.sql
└── ...

backend/migrations/postgres/
└── 001_rls.sql
```

Migration rules:

1. A new case is created by copying/initializing the current schema into a fresh SQLCipher `case.db`.
2. The migration runner opens the case DB, verifies the SQLCipher key, enables foreign keys, WAL and a busy timeout, then applies migrations in numeric order.
3. A `schema_migrations(version, checksum, applied_at)` table records every applied migration.
4. Migration files are immutable after release; corrections require a new migration.
5. Migration checksum is recorded to detect local tampering.
6. Migrations run before the case is opened for normal work.
7. Failed migrations leave the case unavailable rather than partially exposed.
8. Every migration is tested against a clean database and a representative upgraded database in CI.
9. SQLCipher + FTS5 is a CI gate because encryption compatibility is a build requirement.
10. PostgreSQL migrations are maintained separately because SQLite and PostgreSQL differ in encryption, FTS and RLS capabilities.

## 9. Keys and encryption

The architecture requires encryption at rest for the structured DB and vault. P0 should derive a local master key from a startup passphrase using **Argon2id** with parameters recorded in configuration metadata. The derived key is supplied to SQLCipher and used to unwrap the case vault key.

The Chroma index has no assumed native database encryption guarantee in this design. Its directory therefore relies on OS/volume encryption; the deployment must document that requirement. The embedding model and vector files are hash-verified at startup.

The SQLCipher build used by the project must be tested specifically with FTS5 in CI. If the selected SQLCipher build cannot provide the required FTS5 support, the build is rejected rather than silently falling back to plaintext SQLite.

## 10. Seed data

P0 seed data is intentionally small and deterministic:

1. **Privacy defaults:** L2 for every new case; L0 is never seeded as active.
2. **System configuration:** no user PII and no real evidence.
3. **Legal corpus:** imported only from curated, versioned source files; each import records source/version/hash. The migration itself does not embed a large legal corpus.
4. **Benchmark corpus:** synthetic/public benchmark data is outside production case DBs. Benchmark metadata is recorded in `benchmark_runs`.
5. **No sample investigator account with a real credential** is created by the migration.

## 11. Account deletion / case deletion

The PRD is primarily single-user/local and does not define a full account system. Therefore P0 implements **local principal deletion** as a controlled case/data deletion operation rather than cloud-style account cascading.

When a principal requests deletion:

1. Require explicit confirmation and local authentication.
2. Mark affected cases `DELETED_PENDING`.
3. Stop/cancel jobs for those cases and prevent new work.
4. Export/retain an operator-selected audit package if required by the investigator's retention policy.
5. Delete the case database, content-addressed evidence objects, Chroma directory, vault, reports, exports and job artifacts.
6. Securely remove the case encryption key; cryptographic key destruction is the primary guarantee for encrypted remnants.
7. Remove case-specific model/index metadata and cached derived artifacts.
8. Remove the principal's non-sensitive ownership metadata from any global local account store if one exists.
9. Verify that no case directory remains and record only the minimum deletion completion metadata outside the deleted case.

The legal KB is global read-only reference data and is not deleted when a case/principal is deleted.

## 12. Reproducibility metadata that belongs with investigations/reports

The database stores references needed to reproduce an investigation, while large model artifacts remain in the model directory. A completed report must include/hash:

- model name and file hash;
- embedding and reranker hashes;
- llama.cpp build/version;
- backend version and app commit;
- parser and NER versions;
- legal KB version/source hashes;
- prompt-template version;
- deterministic seed and generation parameters;
- top-K and reranker configuration;
- RRF `k`;
- Chroma HNSW parameters;
- thread count/hardware information;
- privacy level;
- query IR version;
- predicate compiler version;
- audit chain head hash and report content hash.

## 13. Schema cannot fully support yet

The schema intentionally does **not** fully model or provide first-class storage for several PRD items:

- **Stretch hypothesis engine:** no `hypotheses`/hypothesis-evidence tables; this is intentionally deferred.
- **Graph-augmented retrieval:** the entity/event relationship tables support basic entity views, but there is no dedicated graph database or graph index.
- **Hindi/Hinglish multilingual retrieval:** no language-specific model/version tables beyond reproducibility metadata.
- **EVTX/PCAP ingestion:** the schema can store normalized events from converted inputs, but it does not model native EVTX/PCAP structures because native ingestion is out of scope.
- **Full dual-LLM quarantine:** no separate trust-domain/model-run schema is provided; this architecture is explicitly deferred.
- **Distributed investigation/collaboration:** there are no multi-node locks, shared workspaces, teams or full RBAC tables.
- **SIEM/SOAR integration:** no connector/case synchronization schema.
- **Federated/private retrieval:** no remote repository identity or synchronization tables.
- **Automatic court admissibility/legal certification:** the report schema can store the BSA s.63 draft and hashes, but the schema cannot establish admissibility or legal validity.
- **External account lifecycle:** the PRD does not specify an identity provider, password reset, multi-user tenancy or cloud account model.

These are deliberate scope boundaries, not missing P0 tables.
